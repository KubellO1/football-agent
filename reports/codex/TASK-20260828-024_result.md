### Provider 状态

监控日志在审计窗口内持续把 Odds-API.io 和 The Odds API 标为 degraded，
当前数据库 `odds_snapshots=0`。赛前日志虽出现少量 `matched`，但 snapshots
仍为 0，说明 event 匹配和最终可写报价之间仍有断点。

### 缺失数据是否重复惩罚

- WeatherAPI、伤病没有直接进入当前数值 completeness/Gate，未发现重复扣分。
- 阵容使用阶段感知 hard gate；初始阶段不强制阵容，未发现被重复计入评分。
- xG 并非按真实可用性评分；当前 builder 把实际 goals 写入 xG 字段。这是数据
  provenance 实现缺陷，违反“无真实 xG 则 UNKNOWN/NULL”的原则，应另立任务。
- completeness 同时影响 decision score、显式 completeness gate 和 risk level，
  属于重复影响；是否过度必须用完整历史样本校准，当前不能凭感觉修改。

### 单位与公式

- EV 使用 `model_probability * decimal_odds - 1` 的单位收益，Gate 调用明确传入
  `expected_value_per_unit`。
- 概率为 0–1，赔率为 decimal odds，单位一致。
- Kelly 经 quarter-Kelly 后受配置 cap 3% 限制。
- 无赔率时不产生 EV/Kelly，也不能成为 BET。

### WATCH 与 reason codes

- DB 中 `WATCH` 与 `NO_ODDS_TRUE` 分开保存，没有证据表明 WATCH 普遍被错误
  归入 NO BET。
- RecommendationGate 返回中文自由文本，而不是完整结构化 reason code。
- `decision_logs=0`，不能对历史每一道 Gate 做逐候选重放。
- 无 selection 的日志不保存 aggregate model probabilities，因此“model
  probability available”只能报告持久化可审计数为 0，不能证明运行时一定为 0。

## 建议

1. **保持当前所有生产阈值。** 当前没有可校准证据。
2. 独立 P0：只针对 Odds-API.io event mapping → multi response → Bet365 quote
   → snapshot persistence 做端到端审计/修复。
3. 独立审批：解决“Bet365 only”与“minimum bookmakers=2”的配置契约矛盾；
   不应在本任务中静默降低验证门槛。
4. 独立 observability 任务：持久化 funnel stage、结构化 reason code、aggregate
   probabilities、真实 provider source，并恢复 decision_logs。
5. 独立数据质量任务：停止用 goals 冒充 xG；无真实 xG 时保持 NULL/UNKNOWN。
6. 收集足够完整且已结算的 shadow 样本后，再评估阈值，至少报告 ROI、Brier、
   CLV 和 Max Drawdown。
